# Design System

## Purpose and scope
Specify original accessible tokens/components. This skill does not grant permission to implement. The project owner must explicitly approve each implementation phase.

## When to use / when not
Use: new or revised visual patterns. Do not use for unrelated projects, speculative content, or unapproved application implementation.

## Required inputs
Master §3, design-system specs. Always read `CLAUDE.md`, `docs/source/MASTER_INSTRUCTION_V1.md`, and `docs/decisions/OPEN_DECISIONS.md`. If approved research is needed and missing, stop and log the dependency.

## Procedure
1. Confirm current phase, approval state and input provenance.
2. Inventory existing files and check current official documentation where external compatibility matters.
3. Review contrast; define tokens; specify component states; map keyboard and responsive behavior.
4. Produce a narrow file-by-file plan and request approval before implementing changes.
5. After approved work, review security, accessibility, data integrity and cross-layer contracts.
6. Record actual verification evidence, unresolved risks and handoff to the next owner.

## Outputs
Expected files: docs/design-system/. Keep proposed versus implemented status explicit.

## Verification
Contrast review and accessibility checklist planned. Only claim a command passed when it actually ran; otherwise mark NOT RUN. Review against the Master and requirement IDs.

## Common failures and handoff
No employer branding or unverified WCAG claim. Never invent citations, installed tools, test results or approved decisions. Handoff includes scope, file list, evidence, missing approvals and next action.
